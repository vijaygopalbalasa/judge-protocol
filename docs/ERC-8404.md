# ERC-8404 profile

[ERC-8404](https://github.com/ethereum/ERCs/pull/1980) (Recomputable Verification Receipts, a
Draft by Pavlo Tvardovskyi) defines a six-field receipt that anyone holding the pinned inputs can
recompute. On Ethereum Magicians the ERC's author suggested a narrow profile over the Judge's four
deterministic checks. This is that profile, `judge-protocol-rvr-v0`, in
[`rvr/profiles/judge-protocol-rvr-v0`](../rvr/profiles/judge-protocol-rvr-v0). It uses the layout
of the author's reference repository (pipavlo82/recomputable-verification-receipts): copied unchanged into
that repository at commit `287c0ea`, the folder passes its own gate and the repository's own tests
and profiles still pass. The author reviewed it independently at the exact PR head and merged it into
the reference repository on 2026-09-28 (pull request #9). `SPEC.md` in that folder is the authority.

## What a receipt says

- **Proposition:** the deliverable the provider committed to on the ERC-8183 job meets the job's
  criteria under `length`, `contains`, `schema` and `checksum`. `VERIFIED` when the score is at or
  above the threshold, `REFUTED` when it is below, `UNVERIFIABLE` when the chain snapshot or the
  deliverable is committed as unavailable.
- **Evidence closure:** a canonical chain snapshot (the job, the provider's submit commitment and
  the verdict, read at one named block) and the deliverable bytes. Recomputation never reads a chain.
- **`http-endpoint` is outside v0.** The judge records a live probe's result, and a recorded result
  is not a reproduced probe, so such criteria are a gate rejection, never a receipt.
- **`json` is outside v0.** The judge added the `json` check after v0 was fixed, so v0 does not
  know its kind and rejects such criteria at the gate, never with a receipt. A later profile
  version would pin it (its rules are already implementation-neutral: docs/CRITERIA.md).
- **Gates, not outcomes:** a job that does not name JudgeEvaluator, malformed or out-of-scope
  criteria, a missing or mismatched commitment, and a snapshot that is not canonical or does not
  describe one chain state are rejected before any outcome. `DIVERGED` means the evaluation
  completed and a candidate identity or the result differs from the receipt's; a gate failure is
  never `DIVERGED`.

## The eight verdict fields

| Verdict field | In the receipt |
| --- | --- |
| `jobId` | the claim; equal to the snapshot's job and submission; part of the `evidenceHash` preimage |
| `criteriaHash` | the claim; recomputed in the result |
| `deliverable` | the claim's commitment; recomputed as keccak256 of the deliverable |
| `score`, `threshold`, `pass` | recomputed in the result; `pass` is the outcome |
| `evidenceHash` | recomputed in the result |
| `timestamp` | the snapshot only: recorded, not re-derived |

The recorded verdict stays in the snapshot, and the result says whether it agrees with the
derivation on the seven fields a derivation can check, so a verdict that disagrees is shown rather
than trusted.

## Why it matches the live judge

- The adapter is a separate, standard-library Python implementation of `SPEC.md`; it does not
  import the judge's code. Its gate re-derives jobs 186779 (a pass) and 186780 (a rejection),
  including the keccak256 `criteriaHash` and `evidenceHash`, and both recorded verdicts come back
  `MATCHES`.
- A cross-implementation test (`judge-service/test/rvr-crosscheck.test.js`) runs the judge's own
  ruling path and the adapter side by side on the 31 semantic vectors, seven real rulings (those
  two plus five earlier ones from the judge's stored evidence) and 400 generated cases. The generated criteria are raw text, so spellings like `1.0`, duplicate keys,
  `__proto__` members and very long numbers reach both parsers. Every ruling agrees, keccak for
  keccak, and every refusal has the matching reason.
- The keccak preimages have their own named encoding, `judge-protocol-sorted-json-v1`, which pins
  an ECMAScript detail that is easy to miss: integer-like object keys come first, in numeric order.
- Word characters for whole-word matching come from a table pinned to Unicode 17.0.0, which the
  judge, the in-browser verifier and the adapter share, instead of each runtime's own Unicode data.
  The gate gives the same result on Python 3.9 through 3.14 (Unicode 13.0 to 16.0).
- The gate runs 31 conformance cases that cover each of the ERC's twelve requirements, 31 semantic
  cases, 74 gate cases (negative cases for the validation rules, snapshot rules and bindings) and
  5 byte-contract known answers computed by the judge's code.
- [`rvr/mutants.py`](../rvr/mutants.py) makes 112 deliberate changes to the adapter: removing
  protections one at a time, plus shortcuts a Python reimplementation could plausibly take (banker's
  rounding, `str.split`, the runtime's Unicode tables). Each must fail the gate in the case written
  to catch it, and all 112 do.

## Run it

```bash
cd rvr
python3 profiles/judge-protocol-rvr-v0/adapter.py --check
python3 profiles/judge-protocol-rvr-v0/test_profile.py
python3 mutants.py
```

CI runs all three on every push. The gate prints the receipts for both base jobs and for the
unavailable-deliverable case. To freeze another ruling, `cd judge-service` and run
`node src/rvr-snapshot.mjs <jobId> --out <dir>` (read-only, needs no keys). It checks the chain id
with the RPC, pins every read to one block, and refuses to write a snapshot if the block changed
while it read.

## Limits

- The ERC is a Draft. Its author reviewed this profile and merged it (see above); that is review of
  the profile, not an audit of the judge.
- Testnet only, and both base vectors are my own test jobs.
- v0 excludes `http-endpoint` checks and criteria with numbers that are not safe integers. It also
  declines `schema` deliverables nested or bracketed deeper than 512, which the judge itself rules on.
- The receipt binds the snapshot by digest but does not prove it matches the chain; checking it
  against Arc is a separate step.
- The profile does not verify the verdict's EIP-712 signature, so it does not establish who signed.
- Word characters follow Unicode 17.0.0. A character first assigned in a later version is not a
  word character until a later profile pins a newer table.
- The live judge does not emit these receipts; the adapter produces them from snapshots.
