# ERC-8183 conformance suite

ERC-8183 (Agentic Commerce, a draft) says in its Specification section what an escrow SHALL do: who may call each
function, in which state, and where the money goes. This suite turns each of those rules into one Foundry test and runs
the same tests against any implementation, on a local fork of the chain it is deployed on. Nothing is sent to any
chain: every job in a run is created on the fork and disappears with it.

It exists because the rules are easy to read and easy to drift from. The ERC's own reference code, and the deployments
copied from it, do not follow four of them; the matrix below shows where each live escrow stands today.

## Read the results first

- A failed rule is a difference from the draft, not by itself a vulnerability. Several are deliberate design choices,
  and the notes below say which ones can move money.
- The draft can still change. The suite follows `ERCS/erc-8183.md` at commit `a078cab` (ethereum/ERCs).
- Forked at the blocks given above the table. A later upgrade of an upgradeable escrow can change its column.
- On Arc, the tests put a standard ERC-20 at the USDC address (`0x3600...`), because a local fork cannot move Arc's
  native USDC. The escrow under test is the deployed bytecode on real chain state. On Base the real USDC is used.
- The suite checks the core state machine and the money it moves. Hooks, fees beyond "only on completion", events
  other than the deliverable, and admin powers are outside it for now.

The full table, as generated by `node contracts/script/conformance-matrix.mjs`, is in

| Circle, Arc testnet | `0x0747EEf0706327138c69792bF28Cd525089e4583` | 25/29 | the same four as the reference code |
| ArcBounty, Arc mainnet | `0x64cA39Fc57315D0D488acCaC07c37C6E841CD058` | 25/29 | the same four as the reference code |
| G2 Jobs, Arc mainnet | `0xac1d948e8127A173f6a594445277476aaE5353EB` | 28/29 | no refund for submitted work at expiry (by design, see below) |
| Virtuals AgenticCommerceV3, Base | `0x238E541BfefD82238730D00a2208E5497F1832E0` | 22/29 | evaluator may be zero; client cannot set the budget; zero-budget jobs funded and submitted to; provider may reject an Open job; submitted work is refundable only 15 minutes after expiry; an Open job can be "refunded" into Expired |

The suite also runs against an escrow written from the Specification section alone
(`contracts/test/conformance/helpers/SpecEscrow.sol`), with and without a platform fee, on every `forge test`. It
passes all 30 tests, and each of 34 single-rule violations planted in it, one at a time, makes at least one test fail.
So a failing test on a real escrow is about the escrow, not the suite.

## What each difference means

**No `expectedBudget` check in `fund` (reference code, Circle, ArcBounty).** This is the one that can move money. The
draft has the client pass the budget it agreed to, and `fund` revert if `job.budget` differs ("front-running
protection"). The reference code's `fund(jobId, optParams)` has no such argument, so `fund` pulls whatever the budget is
when the transaction lands. While a job is Open, the provider may still call `setBudget`; a client who has approved the
escrow for more than the agreed price can be charged the higher amount. Clients of these escrows should approve
exactly the agreed budget, right before funding. The mismatch between the draft and its reference code was also noted
on Ethereum Magicians (t/27902, post 425).

**Only the provider may set the budget (reference code, Circle, ArcBounty, Virtuals).** The draft lets the client or
the provider call `setBudget`. Here the client cannot propose a price. No money moves differently.

**Zero-budget jobs (reference code, Circle, ArcBounty, Virtuals).** `fund` accepts a budget of 0, and `submit` accepts an
Open job whose budget is 0. Both run a job with nothing in escrow, which is useful for free or test jobs (the first two
Judge Protocol rulings on Arc mainnet were such jobs). The draft requires a non-zero budget and a Funded job.

**No refund for submitted work at expiry (G2 Jobs).** By design: once the provider submits, the job settles to the
provider if the evaluator stays silent past the review window (`settle()`), and `claimRefund` covers only work that was
never submitted. The provider is protected from a silent evaluator; the client is not refunded for submitted work. G2
explains this choice on Ethereum Magicians (t/27902, post 428).

**Virtuals AgenticCommerceV3.** The evaluator may be zero, in which case `submit` completes the job at once and pays the
provider. The provider may reject an Open job. Submitted work becomes refundable 15 minutes after `expiredAt`
(`EVALUATOR_GRACE_PERIOD`), which delays a refund by that long. `claimRefund` on an Open job moves it to Expired (no
money is involved, since an Open job holds none). Outside the draft's scope, the contract can also be paused by its
admin, and while paused the admin can withdraw escrowed tokens (`emergencyWithdraw`).

## Run it

```bash
cd contracts
forge test --match-path 'test/conformance/*'                    # the suite's own check (always runs)
ERC8183_CONFORMANCE=1 forge test --match-contract ConformanceReferenceImplementation -vv
ERC8183_CONFORMANCE=1 ARC_TESTNET_RPC=https://rpc.testnet.arc.io ARC_MAINNET_RPC=https://rpc.mainnet.arc.io \
  BASE_RPC=https://mainnet.base.org forge test --match-path 'test/conformance/*'
node script/conformance-matrix.mjs > ../docs/conformance-matrix.md   # regenerate the table
```

Each target skips unless `ERC8183_CONFORMANCE=1` is set, and a fork target also skips without its RPC variable, so a
failing rule never breaks the build.

## Add an implementation

Write a contract in `contracts/test/conformance/Targets.t.sol` that inherits the closest existing shape:

- `ReferenceShapes`: the reference code's calls (`fund(jobId, optParams)`, a 9-field `getJob`). Override `_fundData` if
  your `fund` takes `expectedBudget`.
- `ArcFork`: a deployment on Arc paid in Arc USDC; give it the RPC variable, the chain id and the escrow address.
- For anything else, implement the calls in `ERC8183Conformance.sol` (`_createJobData`, `_setBudgetData`, `_fundData`,
  `_submitData`, `_completeData`, `_rejectData`, `_claimRefundData`, `_job`, `_giveTokens`).

Then add a column for it in `contracts/script/conformance-matrix.mjs`. The tests themselves never change per
implementation.
