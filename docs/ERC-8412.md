# ERC-8412 profile

[ERC-8412](https://github.com/ethereum/ERCs/pull/2002) (Preregistered Acceptance Criteria, a
Draft) freezes a task's acceptance criteria and typed evidence obligations on chain before any
evidence exists, then records the verdict itemized against them, so anyone can refute a verdict
from the published record. A Judge Protocol job already has that shape: the client writes the
checks into the ERC-8183 job at `createJob`, and the judge's verdict is a per-check result. This
profile writes a Judge ruling as ERC-8412 documents and attests it on an ERC-8412 registry.

Built against the draft at commit `ff9fbc7` of that PR. Code: `judge-service/src/erc8412.js`.

Each run is real transactions in this order: the client creates the job, the client
preregisters the criteria document, the provider submits, the judge rules and settles the
escrow, and the judge attests. The package holds the chain state read back from the registry,
the three documents, and every transaction hash. Both packages are valid under the ERC's
reference verifier and under ours, and both Judge verdicts recompute with the Judge verifier.

## Mapping

- **taskRef**: `keccak256(abi.encode(chainId, acpAddress, jobId))`, one ERC-8183 job.
- **Author**: the ERC-8183 client. It preregisters after `createJob` and before the provider
  submits, so every piece of evidence is younger than the criteria (O1).
- **Verifier**: the judge's signing key, the key JudgeEvaluator accepts verdicts from
  (`0xACD5a92c2bD5B5D30A91A49190936dCf85Dfe200` in the runs above). It is never the author.
- **Obligations**: one per check, in the same order. A deterministic check (`length`,
  `contains`, `schema`, `checksum`) is a `DOCUMENT` with `mediaType`
  `application/octet-stream`: its evidence is the delivered bytes. A live `http-endpoint` probe
  is an `AGENT_LOG` whose `agentBinding` is the verifier: its evidence is the judge's own record
  of the probe. The check exactly as the client wrote it sits under the constraint key
  `io.github.vijaygopalbalasa.judge.check`. Nothing is waivable, so `waiverAuthority` is null.
- **Required**: a check is required when failing it alone fails the job. The judge's score only
  falls as checks fail, so a required check that fails always fails the job (E4 holds).
- **decisionRule**: `ALL_REQUIRED` whenever it gives the judge's answer, which is always the case
  at `passThreshold` 100. `ALL_REQUIRED_AND_AT_LEAST(k)` when the optional checks have equal
  integer weights. Otherwise the judge's own rule, defined below.
- **expiry**: the job's `expiredAt`. `terminalOnExpiry` is `REFUND_WITH_RECORD`: when the judge
  cannot rule it abstains, ERC-8183 refunds the client at expiry, and anyone can resolve the
  record to `ExpiredUnresolved`, kept apart from `NotSatisfied`. The judge never attests
  `Indeterminate`.
- **io.github.vijaygopalbalasa.judge.criteriaHash**: the hash the on-chain Judge verdict commits
  to, so the ERC-8412 record and the ERC-8183 verdict name the same criteria.
- **Evidence bundle**: for a deterministic check, the item is the provider's deliverable: its
  `digest` is the bytes32 the provider submitted to ERC-8183, its locator is the deliverable URI,
  and its timestamp is the submit block's. For a probe, the item is the judge's record
  (`check`, `kind`, `pass`, `detail`, `judgedAt`), carried inline, with `digest` the keccak256 of
  its canonical JSON and the verdict block's timestamp.
- **Attestation**: PASS is `Satisfied` and REJECT is `NotSatisfied`, with each check `MET` or
  `UNMET`, no waivers and nothing undecided. The profile refuses to attest a verdict that its own
  decision rule contradicts.
- **Integers only**: ERC-8412 documents carry integers only, so criteria with a non-integer number
  (a weight of 0.5, say) are refused by this profile.

## io.github.vijaygopalbalasa.judge.weighted-threshold-v1

The judge's pass rule from [CRITERIA.md](CRITERIA.md), for criteria no standard rule describes
exactly. Its inputs are in the criteria document: each obligation's weight (the `weight` of its
check, default 1) and the top-level `io.github.vijaygopalbalasa.judge.passThreshold` (default
100). A check passes when its outcome is `MET` or `WAIVED`.
`score = round(100 * passing weight / all weight)`, at most 99 unless every check passes, and the
verdict is `Satisfied` when `score >= passThreshold`, otherwise `NotSatisfied`.

## Check it yourself

```bash
cd judge-service && npm ci
python3 test/fixtures/erc8412/reference/verifier/verify.py ../docs/erc8412/job-186777.json
node --test test/erc8412.test.js
```

A new run needs testnet keys for a client, a provider and an authorized judge signer:
`node --env-file=.env src/erc8412-live.mjs --registry 0x48c3a1812F2dFc762a80dbD5c65e9C7B0BB25ae4 [--reject]`.

The tests pin the interoperability claims: our canonical JSON reproduces the reference digest of
all 69 documents in the ERC's 23 conformance packages; our independent JavaScript checker reports
exactly the violations each of those packages expects; the packages we emit pass the ERC's own
verifier; and for 400 random criteria the decision rule gives the judge's answer for every
combination of check outcomes. The reference vectors and verifier are vendored, unchanged and
CC0, in `judge-service/test/fixtures/erc8412/`.

## Limits

- ERC-8412 is a Draft. When its interface changes, this profile has to follow.
- Testnet only, and both jobs are my own test jobs.
- The live judge does not yet publish an ERC-8412 record for every ruling. The runs above use a
  script that drives the same engine the live service runs.
- A probe result is recorded, not re-derivable: the record says what the judge saw, not what the
  endpoint returns today.
- The registry is the ERC's reference contract, which its README calls unaudited.
